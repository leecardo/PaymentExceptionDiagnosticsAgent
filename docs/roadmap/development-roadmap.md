# 支付异常诊断 Agent 后续开发路线

## 1. 路线原则

- 使用可运行、可验证的纵向切片推进；
- 每个阶段交付真实行为，不提交占位接口或假诊断结果；
- 先实现确定性证据收集，再引入模型自主选择；
- 先完成只读诊断，再考虑需要人工审批的动作；
- 每个 Agent 能力同时补充测试、审计和评测；
- 技术复杂度只有在可测收益成立时增加。

## 2. 当前基线

已具备：

- Java 21 + Spring Boot 3.5.16 Maven 多模块；
- LangChain4j OpenAI 兼容配置；
- 独立 Java MCP Server 与 `/mcp`；
- PostgreSQL + pgvector 本地编排配置；
- Vue 3 + TypeScript 状态页面；
- 领域证据基础模型；
- API、MCP 和前端构建验证。

当前限制：

- 尚无支付业务表和查询；
- MCP 没有业务 Tool；
- Agent 工作流、RAG、审批和评测尚未实现；
- 当前开发环境缺少 Docker，数据库容器尚未实际验证。

## 6. M2：支付流水与规则诊断

目标：联合订单和支付流水，通过确定性规则判断第一批异常阶段。

### 数据与领域

- [ ] 增加 `payment_transactions`；
- [ ] 建立支付渠道、交易类型和交易状态；
- [ ] 定义订单与支付流水关联规则；
- [ ] 扩展 `DiagnosisStage`。

### 应用工作流

- [ ] 查询订单；
- [ ] 查询关联支付流水；
- [ ] 生成 `DiagnosisEvidence`；
- [ ] 实现规则诊断器；
- [ ] 输出阶段、证据和规则编号。

第一批规则：

- 订单存在但没有支付流水；
- 支付处理中超时；
- 第三方成功但回调未接收；
- 回调成功但订单状态未更新；
- 支付失败并有明确渠道错误。

完成标准：

- 每条规则有行为测试；
- 每个结论至少关联一条证据；
- 证据不足时不强制判断；
- 此阶段不依赖 LLM，也能完成确定性诊断。

## 7. M3：消息和补偿链路

目标：覆盖支付完成后的异步消息、消费和补偿状态。

任务：

- [ ] 增加 `message_deliveries`；
- [ ] 增加 `compensation_tasks`；
- [ ] 定义 `MessageQueryPort` 和 `CompensationQueryPort`；
- [ ] 增加消息未发送、发送失败、未消费和消费失败规则；
- [ ] 增加补偿未创建、待执行、执行失败和超过重试上限规则；
- [ ] 把异步链路证据加入诊断结果；
- [ ] 在前端按时间线展示证据。

可靠性要求：

- 消息和补偿查询失败不能被解释成业务失败；
- 区分“数据不存在”“上游不可用”“查询超时”；
- 重试次数和最后错误必须可见；
- 不在此阶段执行补偿。

## 8. M4：Java MCP 业务工具

目标：将已经验证的查询用例暴露为 MCP 白名单工具。

计划工具：

- [ ] `get_order`；
- [ ] `get_payment_transactions`；
- [ ] `get_message_delivery`；
- [ ] `get_compensation_tasks`；

每个 Tool 必须完成：

- [ ] 清晰名称和描述；
- [ ] JSON Schema 输入；
- [ ] 参数长度、格式和白名单校验；
- [ ] 结构化返回；

- 非法参数和权限不足都有协议级测试；
- 工具列表与实现完全一致。

## 9. M5：LangChain4j Agent 工作流

目标：模型根据用户问题和工作流状态选择工具，将工具事实组织为可解释结论。

实施顺序：

1. 固定工作流调用全部必要工具；
2. 让模型只负责证据解释；
3. 建立初始评测集；
4. 只有固定工作流不能处理的问题明确出现后，再允许模型选择工具。

任务：

- [ ] 定义 `DiagnosisRun` 状态；
- [ ] 定义模型输入和结构化输出；
- [ ] 建立 MCP Client；
- [ ] 建立允许工具集合；
- [ ] 设置最大步骤、总超时和 Token 上限；
- [ ] 防止重复工具调用循环；
- [ ] 保存模型与工具调用审计；
- [ ] 强制结论引用证据 ID；
- [ ] 证据不足时返回 `INSUFFICIENT_EVIDENCE`；
- [ ] 模型不可用时保留规则诊断结果。

完成标准：

- 模型不能调用未注册工具；
- 工具失败不会造成无限循环；
- 结论中的事实均可追溯；
- 关闭模型后确定性规则仍可使用；
- 固定用例集得到可重复结果。

## 12. M8：评测与可观测性

目标：让模型、Prompt、工具和知识库变更的影响可测量、可回归。

### 评测数据集

至少覆盖：

- 订单不存在；
- 未发起支付；
- 支付处理中超时；
- 第三方成功但回调缺失；
- 订单回写失败；
- 消息发送和消费失败；
- 补偿未执行或失败；
- Trace 缺失；
- 工具无权限；
- Prompt Injection；
- 无答案知识问题。

### 指标

- [ ] 异常阶段准确率；
- [ ] 工具选择正确率；
- [ ] 工具参数正确率；
- [ ] 任务完成率；
- [ ] 无依据结论率；
- [ ] 引用准确率；
- [ ] P50/P95 延迟；
- [ ] 平均工具调用次数；
- [ ] Token 和单任务成本；
- [ ] 审批拦截次数。

### 可观测性

- [ ] 为 API、Agent、MCP、工具和数据库传播 Trace ID；
- [ ] 记录工作流状态转换；
- [ ] 记录工具耗时和错误分类；
- [ ] 记录模型名、Prompt 版本、Token 和成本；
- [ ] 支持失败 Run 回放；
- [ ] 建立延迟、错误率和成本看板。

完成标准：

- 每次模型、Prompt、工具或知识库变更可运行同一评测集；
- 结果可与上一次基线比较；
- 任一失败结论可追踪到工具、检索和模型步骤。

## 14. 推荐迭代顺序

严格按以下顺序推进：

```text
数据库运行验证
  → 订单查询
  → 支付规则诊断
  → 消息与补偿证据
  → MCP 工具
  → Agent 工作流
  → SSE 与审批
  → RAG
  → 评测与可观测性
  → 可演示发布
```

不要同时开发多个未完成方向。一个里程碑只有在代码、测试、运行验证和文档同步完成后才进入下一阶段。

## 15. 每个里程碑的完成定义

每个里程碑必须同时满足：

- 行为可运行；
- 有针对可观察契约的测试；
- 有实际服务或浏览器烟雾验证；
- 错误和边界条件明确；
- 没有真实密钥或敏感数据；
- 不存在假结果、空实现或误导性能力声明；
- README、设计文档和路线状态已同步；
- 简历只写已经完成且可解释的成果。
